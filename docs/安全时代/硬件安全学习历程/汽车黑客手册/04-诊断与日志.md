## 01-DTC-诊断故障码

### 1.1-DTC与MIL

当汽车发生故障，ECU 在处理完成故障后，会编码事件保留为 DTC 作为事发证据，类似于飞机的“黑匣子”

- DTC：记录故障的代码
- MIL：故障指示灯，即发动机故障灯

出现 DTC 不一定导致 MIL 亮起，维修时不能只看 MIL 是否亮起

### 1.2-硬故障与软故障

软故障：间歇性问题，如油箱盖没拧紧

硬故障：不主动干预就不会消失的问题

按照非官方分类，故障可以分为A、B、C、D四种级别：

- A：立刻点亮 MIL
- B：多次触发则点亮 MIL
- C：发出部分简单的提示信息，不点亮 MIL 
- D：完全不点亮 MIL，也没有提示信息

### 1.3-冻结数据帧

在存储 DTC 时，PCM 会对整车所有部件快照，这样，即便发动机出现问题，排查时也能知道例如转速，温度等信息。

可以保存的內容很多很多，这里不列出

### 1.4-DTC 格式

| **字节位置** | **描述**                                                     |
| ------------ | ------------------------------------------------------------ |
| 1            | P (0x0) = 动力总成，B (0x1) = 车身， C (0x2) = 底盘，U (0x3) = 网络 |
| 2            | 0、2、3（SAE 标准） 1、3（制造商自定义）                     |
| 3            | 位置 1 的子分组                                              |
| 4            | 具体故障区域                                                 |
| 5            | 具体故障区域                                                 |



在 CAN 上，ECU 传输二进制数据，对于一份 DTC，原始数据仅有 2 Bytes。DTC 使用位字段编码解码，和协议解析器其实很类似，以标准 OBD-II 两字节编码为例：

2 bytes 总计 16 bit，前2位决定系统类别，3-4位决定数据还是字母，剩余12位组成剩下3个十六进制数字对应编号

```tex
原始字节：0x04 0x77

二进制：
00000100 01110111

00 | 00 | 0100 | 0111 | 0111
 P    0     4      7      7
```

### 1.5-诊断仪

入门款可以选择 ELM327，约￥40，再配上一些奇妙小软件或者适配器。

技师检查会用到诊断仪来读取 DTC，但对于 Car Hack 来说不是必选项。

诊断仪有 DTC 擦除功能，如果 DTC 只在某次出现，后来不再出现，通常会自行擦除。有时候，诊断仪使用擦除功能将 DTC 情况，故障记录消除，但是下次再次出现故障，依然没能解决问题。

## 02-UDS

UDS 统一诊断服务，是应用层协议，在车联网相关的多方资料中都不断被提及

诊断仪通过 UDS 协议与 ECU 沟通，UDS 定义了一套诊断请求和响应的规则，如：

| 任务           | UDS  |
| -------------- | ---- |
| 切换诊断会话   | 0x10 |
| ECU 复位       | 0x11 |
| 读取数据       | 0x22 |
| 读取 DTC       | 0x19 |
| 清除 DTC       | 0x14 |
| 安全访问       | 0x27 |
| 写入数据       | 0x2E |
| 请求下载       | 0x34 |
| Tester Present | 0x3E |



### 2.1-ISO-TP

汽车诊断通信协议栈（简化版）：

```tex
UDS：定义诊断服务：读数据、复位、安全访问等
  ↓
ISO-TP：负责长报文分段、传输和流量控制
  ↓
CAN：负责总线上的帧传输、仲裁和错误处理
  ↓
物理层：CAN 收发器、双绞线、CAN_H / CAN_L 等
```

经典 CAN 帧只能包含 8 Bytes，ISO-TP ：

1. 在发送方，将內容分为多个 CAN 帧
2. 在接收方，重新组合 CAN 帧
3. 还负责流量控制

四种帧类型：

| 类型              | PCI 类型 | 作用                       |
| ----------------- | -------- | -------------------------- |
| Single Frame      | 0        | 单帧即可完成传输           |
| First Frame       | 1        | 多帧传输的起始帧           |
| Consecutive Frame | 2        | 后续数据帧                 |
| Flow Control      | 3        | 接收方控制发送方的传输节奏 |

### 2.2-实测 ISO-TP

```bash
cansend can0 7df#02010d
Replies similar to 7e8 03 41 0d 00
```

各个地方分析看

| 部分 | 含义                                    |
| ---- | --------------------------------------- |
| 7df  | CAN 仲裁 ID，OBD诊断码                  |
| 02   | ISO-TP/OBD 请求中的数据长度，数据包大小 |
| 01   | OBD Mode 01，查询当前数据，模式         |
| 0d   | PID 0x0D，查询车速                      |
| 00   | 车速为0，因为车是静止的                 |

响应包在发送的基础上

- CAN 仲裁 ID 增加 0x08，因此 7df -> 7e8
- 响应成功，类型增加 0x40，因此 0x01 -> 0x41
- 如果响应失败，那么本来 0x41 的位置大概会出现 0x7F（错误响应）

对于 OBD Mode：

| Mode | 功能             |
| ---- | ---------------- |
| 0x01 | 读取当前数据     |
| 0x02 | 读取冻结帧数据   |
| 0x03 | 读取已确认 DTC   |
| 0x04 | 清除诊断信息     |
| 0x07 | 读取待定 DTC     |
| 0x08 | 控制车载系统测试 |
| 0x09 | 读取车辆信息     |
| 0x0A | 读取永久 DTC     |

而对于错误响应，常见 UDS 错误响应如下：

| **十六进制（第 4 字节）** | **缩写** | **描述**                       |
| ------------------------- | -------- | ------------------------------ |
| 10                        | GR       | 一般性拒绝                     |
| 11                        | SNS      | 不支持的服务                   |
| 12                        | SFNS     | 不支持的子功能                 |
| 13                        | IMLOIF   | 消息长度错误或格式无效         |
| 14                        | RTL      | 响应过长                       |
| 21                        | BRR      | 忙，请重复请求                 |
| 22                        | CNC      | 条件不满足                     |
| 24                        | RSE      | 请求顺序错误                   |
| 25                        | NRFSC    | 子网组件无响应                 |
| 26                        | FPEORA   | 故障阻止执行所请求的操作       |
| 31                        | ROOR     | 请求超出范围                   |
| 33                        | SAD      | 安全访问被拒绝                 |
| 35                        | IK       | 无效密钥                       |
| 36                        | ENOA     | 超出尝试次数                   |
| 37                        | RTDNE    | 所需的时间延迟尚未结束         |
| 38-4F                     | RBEDLSD  | 由扩展数据链路安全文档保留     |
| 70                        | UDNA     | 不接受上传/下载                |
| 71                        | TDS      | 传输数据已暂停                 |
| 72                        | GPF      | 一般编程失败                   |
| 73                        | WBSC     | 块序列计数器错误               |
| 78                        | RCRRP    | 请求已正确接收，但响应尚未就绪 |
| 7E                        | SFNSIAS  | 当前会话不支持该子功能         |
| 7F                        | SNSIAS   | 当前会话不支持该服务           |

### 2.3-ISO-TP 工具使用

使用 ISO-TP 工具进行不止一个 CAN Frame 的交互

- isotpsend：发送 ISO-TP 数据包
- isotpsniffer：观察 ISO-TO 通信

终端 A 设置 sniffer：

```bash
isotpsniffer -s 7df -d 7e8 can0
```

终端 B 发送：

```bash
echo "09 02" | isotpsend -s 7DF -d 7E8 can0
```

- 09：OBD mode 09，请求车辆信息
- 02：PID 02，请求 VIN

终端 A 接收：

```bash
isotpsniffer -s 7df -d 7e8 can0
 can0  7DF  [2]  09 02  - '..'
 can0  7E8  [20]  49 02 01 31 47 31 5A 54 35 33 38 32 36 46 31 30 39 31 34 39
     - 'I..1G1ZT53826F109149'
```

- 49：Mode 09 的肯定响应
- 02：对应 VIN
- 01：返回的数据项数量
- 后续字节：VIN 的 ASCII 编码
